# CICS Component Consolidation Matrix

Status: reconstruction/consolidation evidence  
Prepared: 2026-08-25  
Scope: recovered source components preserved under `recovery/donor_snapshots/R1`, `R2`, and `R3`

This document classifies recovered CICS implementation components before any promotion into a canonical `src/` tree. It is not a rebuild plan and does not authorize implementation of missing features.

## Disposition vocabulary

- **KEEP** — recovered logic is sufficiently portable and coherent to retain substantially as-is, though packaging/import cleanup may still be required.
- **ADAPT** — functionality belongs in canonical CICS, but the recovered implementation must be corrected, generalized, consolidated, or given a new interface before promotion.
- **REJECT** — do not promote this implementation into canonical source. Its historical existence remains preserved in `recovery/`.
- **EXTERNAL / HISTORICAL ONLY** — operational convenience, generated/runtime state, or historical evidence that does not belong in canonical product source.

Historical demonstration is based on `CICS_EVIDENCE_INDEX.md` and `CICS_IMPLEMENTATION_STATUS.md`. A family-level demonstration means transcript evidence supports the subsystem or workflow, not necessarily an independent rerun of that exact file today.

## Cross-donor conclusions

1. **R1 artifact governance is a real salvageable subsystem, not a complete CICS architecture.** Its state model and small helper functions are the cleanest recovered code, while the executable scripts need packaging, configuration, provenance, and destructive-operation safeguards.
2. **R2 contains the strongest recovered RAG implementation, but its internal identity contract is broken.** Chat chunking, embeddings, Qdrant loading, and retrieval belong conceptually; they must not be promoted unchanged because ordering, path identity, payload schema, and query/loader compatibility are not stable.
3. **The R2 regex project-extraction lineage is rejected.** The later authoritative-folder registry approach is conceptually stronger, but its recovered builder is syntactically broken and its authority policy is embedded in code.
4. **R3 is the strongest recovered deterministic-control foundation.** Manifesting, hashing, validation, auditing, and determinism belong in canonical CICS, but path-based document identity and corpus-specific configuration must be corrected before promotion.
5. **R1/R2 early coding chunker duplication is proven by identical recovered blob content.** Neither copy should become canonical source.
6. **Runtime checkpoints, generated audit output, and machine/game operational wrappers are evidence, not canonical product source.**
7. **No donor can be copied wholesale into `src/`.** Canonical source-tree design must be assembled from the KEEP/ADAPT set and must resolve the shared identity/configuration contracts before code promotion.

## Gate before canonical source-tree creation

The next reconstruction step is to design a canonical source tree from the KEEP/ADAPT set above. That design must explicitly resolve these cross-cutting contracts before any donor code is moved:

- portable source/document/chunk identity;
- configuration and filesystem-root ownership;
- artifact lifecycle audit/provenance model;
- manifest as the authoritative ordering/identity boundary;
- embedding row ↔ chunk identity binding;
- vector-store payload schema and retrieval interface;
- entity/project authority source and registry schema;
- source vs generated/runtime-state separation.

Until that design is accepted, `recovery/donor_snapshots/` remains the authoritative preservation location for donor code and no donor implementation should be promoted into canonical `src/`.
